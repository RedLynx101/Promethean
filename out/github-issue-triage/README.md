## What this workflow does

When a new GitHub issue is opened on a monitored repo, this workflow:

1. Validates the webhook payload (HMAC + delivery-id idempotency).
2. Classifies the issue as `bug | feature-request | question | security`.
3. For **non-security** issues: parallel fan-out to apply labels, assign a team, and draft a triage response. Converge at a single bot comment post.
4. For **security** issues: pauses at a human-approval gate (Slack), and on approve does the same three actions + pages on-call via PagerDuty. On reject, loops back to re-classify with feedback.
5. If the classifier itself fails, a manual-triage fallback labels the issue `triage:manual` and assigns to `@org/eng-triage`.

Spectrum composition: **7× L0, 1× L2, 1× L3, 1× HumanGate.** Estimated $0.011 / 3.7 s per run, well under the $0.50/run governance cap.


## Honesty notes

This is a **scaffold**, not production-grade:

- The graph runtime in `workflow.ts` is a **minimal in-repo walker** implementing the edge-type semantics (`default / parallel / conditional / error / loop`) from the Promethean spectrum. For production, swap for `@langchain/langgraph` — the node function signatures are compatible, so the migration is mechanical. The scaffold avoids the heavyweight dep so `pnpm install && pnpm test` is fast.
- Classify, drafting, and page nodes **stub their external calls by default** (controlled by env var `LIVE=true`). Default behaviour: deterministic fixtures so the smoke test is hermetic. Flip `LIVE=true` to actually hit Anthropic / GitHub / PagerDuty.
- HumanGate resumes via a **file-based signal** (`./gate-signals/<executionId>.json`) for simplicity. Replace with your team's Slack approval webhook when wiring for real.
- The webhook receiver in `src/index.ts` is an Express stub with HMAC verify. Not production-hardened (no rate-limiting, no auth rotation).

Everything above is called out inline where relevant with `// TODO(production)` comments.
