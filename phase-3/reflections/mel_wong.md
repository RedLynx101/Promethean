## What I would do differently

- **Freeze a "submitter branch" a few days before the deadline for docs-only edits** so the code tag stays clean for the artifact description.
- **Run the pivot decision earlier in Phase 2.** We lost time building toward an execution engine that was never going to ship; catching the "we're promising *deployable* but only delivering *designable*" gap earlier would have let the vault + emit scaffolding land without the Phase-3 time pressure.
- **Capture API/DB traces continuously during dev**, not at the end. The `traces/exports/` folder sat empty until I exported the harness bundle late in the process; had we captured after every scenario run through the UI, the primary Track-A evidence would already be there without an end-of-project sprint.

## Lessons learned

- **Rubric mapping tables** (as in `final_report.md` §9) save time during review and for teammates who own different files.
- **Don't build what you can rent.** The pivot's core insight — stop competing with Temporal/Inngest/LangGraph as a runtime and instead own the curated cookbook — is generalisable. Every time I caught myself designing plumbing that already exists in an adjacent tool, the right move was to cede that territory and narrow to what only we could do.
- **The vault is the product.** Emit output quality ≈ vault quality. That framing changed how I wrote integration notes: less "reference material," more "this is literal input to the code generator, and vagueness compounds." Worth internalising for any future agent-composition work.
- **Honest "this is stubbed" labels outperform polished-but-opaque code.** The `LIVE=true` gate + inline `// TODO(production)` blocks in the emit output do more for reviewer trust than a production-finished demo with hidden rough edges would.
